## [1] MEDIUM · rare · state-rmw
**saveState's previousJobs cleanup deletes another session's just-added job record AND its files (lost-update with collateral unlink)**

- **Location:** `plugins/codex/scripts/lib/state.mjs:106`
- **Interleaving:** updateState (state.mjs:124-128) is load->mutate->save with no lock, and every upsertJob/setConfig/cleanup goes through it. Session A: state = loadState() at T0, jobs = [J1]. Concurrently a detached task-worker for session B (codex-companion.mjs:697-698 or tracked-jobs.mjs:151-152) does writeJobFile(J2.json) then upsertJob(J2), so on disk state.json = [J1, J2] and J2.json + J2.log exist. Session A now runs saveState(cwd, {..stale snapshot.., jobs:[J1']}): line 93 previousJobs = loadState().jobs = [J1, J2] (sees B's write), line 95 nextJobs = pruneJobs([J1']) = [J1'], line 105 retainedIds = {J1}. The loop at 106-112 finds J2 is not retained and calls removeJobFile(J2.json) (110) and removeFileIfExists(J2.logFile) (111). Line 120 then writes state.json = [J1'], dropping J2. Both the delete and the atomic write are outside any lock, so B's write between A's loadState and A's saveState is silently destroyed.
- **Impact:** A concurrent session/background worker's queued-or-running job is erased from state.json and its per-job JSON + log file are physically unlinked mid-run. The worker keeps executing but its progress writes silently no-op (createJobProgressUpdater bails at tracked-jobs.mjs:104-107 when jobFile is gone), its result is orphaned, and because the record vanished from state.json, hasOtherActiveSessionJobs (session-lifecycle-hook.mjs:103) can no longer see it — so an unrelated SessionEnd may tear down the shared broker the worker still depends on. The same lost-update also silently reverts config toggles (setConfig stopReviewGate) whenever the losing writer's stale snapshot wins.
- **Verifier reasoning:** Verified against the actual code. state.mjs updateState (124-128) is an unlocked load->mutate->save; saveState (92-122) re-reads previousJobs via loadState() at line 93 (so it sees writes committed by other processes after the caller's snapshot), derives retainedIds from the caller's STALE state.jobs, then at 106-112 physically unlinks the .json and .log of every previousJobs entry not in retainedIds, then atomically writes state.json (119-120). There is no file locking anywhere (grep for flock/lockfile/.lock returns only false positives). The writers are genuinely concurrent OS processes, not serialized: task-workers are launched with spawn(...detached:true)+child.unref() (codex-companion.mjs:671-682), not spawnSync, so the parent does not block; and Node's single-threaded event loop only serializes writers within one process, not across the worker/main-session/hook processes that all write the shared state.json. So the exact claimed interleaving is constructible: A loads [J1] (updateState:125), B (a detached worker or other session) does writeJobFile(J2)+upsertJob(J2) making disk = [J1,J2] with J2.json/J2.log present, then A's saveState line 93 re-reads [J1,J2] while nextJobs stays [J1'] -> retainedIds={J1} -> J2.json and J2.log unlinked (110-111) and state.json rewritten as [J1'], erasing J2. The downstream impact is accurate: createJobProgressUpdater bails at tracked-jobs.mjs:104-107 once jobFile is gone, and hasOtherActiveSessionJobs (session-lifecycle-hook.mjs) reads state.json directly so the dropped record becomes invisible to broker-teardown protection; setConfig(stopReviewGate) is likewise clobbered when a stale writer wins. The SessionEnd path (cleanupSessionJobs line 53 load -> terminateProcessTree kill -> line 71 saveState) has an especially wide window because a blocking process-kill sits between load and save, and it collides naturally with another session's still-running worker. I mark reachability as rare rather than normal-multisession because, although the setup (one session + a background task, or two agents in one repo) is exactly the plugin's intended usage and nothing serializes it away, each updateState is a short synchronous read-modify-write burst and the destructive overlap only happens when another process's write lands inside that specific load->write window -- it will occur occasionally under heavy concurrent use (many progress upserts, session ends firing while a worker runs) but will not reproduce on most operations or on demand. Not theoretical: real concurrency, no locks, exact interleaving reconstructable from the code.

Inside saveState, previousJobs (state.mjs:93) = current disk state = [..., J_B], but nextJobs (from the S0-derived snapshot) omits J_B, so the state.mjs:106-112 loop unlinks J_B.json + J_B.log and the write omits J_B. The known fixes (hasOtherActiveSessionJobs gate, fail-closed direct read) run at lines 140/98 and do not cover this earlier save.
- **Impact:** The known SessionEnd hardening still leaves a hole: session A's own cleanup save can delete a live job belonging to session B (or B's background worker) that was added after A's loadState. - **Verifier reasoning:** Confirmed against the code. cleanupSessionJobs (session-lifecycle-hook.mjs:53-71) is synchronous, but the competing writer is the detached task-worker (codex-companion.mjs:671-681, detached+unref), a separate OS process — so event-loop/spawnSync serialization does not apply. The known SessionEnd hardening (hasOtherActiveSessionJobs gate line 140, fail-closed read line 98) runs AFTER this save, so it doesn't cover it; worse, since cleanup just dropped J_B, line 140 can miss it and A proceeds to sendBrokerShutdown/teardownBrokerSession, killing the shared broker under B's live worker. Rated 'rare' rather than 'normal-multisession' because the load→save window is only a couple of synchronous fs reads plus a fast process.kill (win32 taskkill widens it) while the worker writes state.json only a handful of times per job, so hitting the interleave needs unlucky timing; the underlying scenario (two sessions in one repo, one ending while the other runs a background job, A owning a job so cleanup doesn't early-return at line 55) is itself normal. It is also partially self-healing (B's next upsertJob re-adds the record; completion recreates the file), which caps persistence.

## [4] MEDIUM · normal-multisession · client-reuse (broker reuse + direct-retry fallback under concurrency)
**Cold-start broker spawn is a check-then-act race: two sessions in the same cwd each spawn a broker, one is orphaned and never torn down**

- **Location:** `plugins/codex/scripts/lib/broker-lifecycle.mjs:114-169`
- **Interleaving:** Session A and Session B (or a session + a detached background task-worker) both do their FIRST broker-backed command in the same cwd with no broker yet. Both call CodexAppServerClient.connect -> ensureBrokerSession. A: loadBrokerSession() returns null (broker.json absent). B: loadBrokerSession() also returns null (still absent). There is no lock/O_EXCL/mkdir-atomic anywhere (grep confirms none). Both then createBrokerSessionDir() (mkdtemp -> two distinct temp dirs / distinct unix sockets), both spawnBrokerProcess(), both waitForBrokerEndpoint() succeed (each listens on its own socket), then both saveBrokerSession() with a plain writeFileSync. The second writer overwrites broker.json; the first broker's endpoint/pid/sessionDir are now lost. The race window is the full spawn+wait (up to 2s at line 149), which is trivially wide for two terminals/sessions opened together.
- **Impact:** A fully-live broker process plus its child `codex app-server` (and unix socket + temp dir + pid file) become untracked: broker.json points only at the second broker, so SessionEnd teardown (which reads loadBrokerSession) only ever kills the tracked one. The orphaned broker + app-server leak for the life of the machine, holding a CODEX_HOME app-server session nobody will reap. This is a NEW leak distinct from the #402 zombie fix (that broker's child is alive, so it never self-exits).
- **Verifier reasoning:** CONFIRMED against the actual code.

Mechanism verified in broker-lifecycle.mjs:113-171. ensureBrokerSession is a genuine check-then-act: loadBrokerSession(cwd) reads broker.json (line 114), and broker.json is written only AFTER spawn + waitForBrokerEndpoint succeeds, via saveBrokerSession -> plain fs.writeFileSync (line 92), which is NOT atomic and is last-writer-wins (unlike saveState in state.mjs:117-120 which deliberately uses tmp+rename). There is no cross-process lock anywhere in the acquisition path — grep for flock/O_EXCL/lockfile/exclusive/atomic-mkdir over broker-lifecycle.mjs, app-server.mjs and state.mjs returns nothing (exit 1). So two processes can both read null and both proceed to mkdtemp -> distinct socket -> spawnBrokerProcess -> saveBrokerSession; the second write clobbers the first.

The usual refutations do NOT apply here because the callers are independent OS processes, not one event loop: each /codex command is its own short-lived codex-companion.mjs invocation, and background tasks spawn a DETACHED task-worker process (codex-companion.mjs:671-682, spawn(..., {detached:true}); child.unref()). Both task and review execute through withAppServer -> CodexAppServerClient.connect(cwd) -> ensureBrokerSession (codex.mjs:613-651, app-server.mjs:336-346). No spawnSync serializes the connect. So process boundaries here CREATE the concurrency rather than prevent it.

The race window is wide, not tight: process 1 writes broker.json only after fork of a node broker + that broker's own CodexAppServerClient.connect(cwd,{disableBroker:true}) spawning and initializing the real `codex app-server` child + server.listen (app-server-broker.mjs:48-68,266-267). That is realistically hundreds of ms to ~2s (line 149 timeout is 2000ms). Any second cold-start that calls loadBrokerSession within that window reads null.

Impact CONFIRMED. The broker has no idle timeout: it self-exits only when its child app-server dies (app-server-broker.mjs:126-136 exitPromise), on broker/shutdown RPC (180-184), or SIGTERM/SIGINT (256-264). SessionEnd teardown reads loadBrokerSession(cwd) and tears down only the broker recorded in broker.json (session-lifecycle-hook.mjs:120-157). After the clobber, broker.json points only at broker #2; broker #1's endpoint/pid/sessionDir are lost, so it is never reaped, and because its app-server child stays alive it never self-exits. Genuine leak: orphaned broker process + codex app-server child + unix socket + temp dir + pid file, holding a CODEX_HOME app-server session. This is distinct from the #402 zombie fix (that fix handles a child that DIED; here the child is alive).

Reachability = normal-multisession. The broker exists specifically to serialize concurrent multi-session codex access, and the code treats multi-session as first-class (state.mjs:114-116 comment about "another session's SessionEnd hook deciding whether the shared broker is still in use"). Concrete reachable interleavings: (A) two terminals/agents in the same repo both firing their first /codex command near session start; (B) single session: two `/codex:task --background` back-to-back -> two detached workers both cold-start (enqueueBackgroundTask spawns a worker immediately, codex-companion.mjs:688); (C) single session: a background task plus a foreground /codex:review within ~1-2s. The only thing keeping this from firing constantly is that cold-start happens once per broker lifetime per cwd — after the broker is up everyone reuses it — so it needs two "firsts" to overlap. Given the wide window that overlap is a realistic occasional coincidence, not exotic.

Severity = medium. It is a real resource leak that silently evades the exact teardown machinery built to prevent broker leakage, and each occurrence strands a long-lived broker+app-server pair (memory + a held CODEX_HOME session) that persists until the app-server child independently dies or the machine reboots; it accumulates across repeated collisions. It is not correctness/data loss and causes no user-visible command failure (the surviving broker works), and it is bounded to one process pair per collision — hence medium rather than high. The report's "leak for the life of the machine" is slightly overstated (the orphan dies if its app-server child ever exits, which would trip the broker's exitPromise), but the untracked-leak core claim is accurate.

## [5] MEDIUM · normal-multisession · client-reuse (broker reuse + direct-retry fallback under concurrency)
**Broker-busy triggers an unconditional direct-retry even for workspace-write tasks, running two Codex agents against the same working tree at once**

- **Location:** `plugins/codex/scripts/lib/codex.mjs:630-649`
- **Interleaving:** Background worker B holds the broker running a write task (executeTaskRun -> runAppServerTurn, sandbox: "workspace-write", codex-companion.mjs:485-495). User launches a second write task A in the foreground. A's withAppServer connects to the shared broker and issues thread/start; broker returns BROKER_BUSY because B owns activeStreamSocket. withAppServer's shouldRetryDirect is true for `transport===broker && rpcCode===BROKER_BUSY_RPC_CODE` (codex.mjs:631), so A spawns its OWN direct `codex app-server` (disableBroker:true) and re-runs the whole fn -> turn/start with sandbox workspace-write.
- **Impact:** The broker exists precisely to serialize app-server access, but the BUSY->direct fallback silently de-serializes write tasks: two agents now apply patches / run shell commands / git operations against the same working tree and index concurrently, which can corrupt in-progress edits or produce interleaved/lost changes. The direct client itself is closed in the finally (no process leak), so the hazard is concurrent mutation, not a leak. The fallback makes no read-only vs workspace-write distinction, so it is safe for reviews but unsafe for /codex:rescue-style write runs.
- **Verifier reasoning:** Confirmed against the actual code. The broker is shared per-cwd (ensureBrokerSession keyed by cwd state dir, app-server.mjs:336-347 / broker-lifecycle.mjs:113-171) and serializes by socket ownership: a turn/start holds activeStreamSocket until turn/completed (app-server-broker.mjs:217-226,90-99), and any other socket's request meanwhile gets BROKER_BUSY -32001 (app-server-broker.mjs:190-202). A thread/start/thread/resume (codex.mjs:741,760) is subject to that check, so a second task's FIRST real request hits BUSY. withAppServer (codex.mjs:630-649) treats broker+BROKER_BUSY as shouldRetryDirect=true and re-runs the whole fn against a freshly spawned direct `codex app-server` (disableBroker:true, cwd unchanged) — so the second workspace-write turn (executeTaskRun -> runAppServerTurn sandbox workspace-write, codex-companion.mjs:485-495) runs concurrently with the first. Background tasks spawn immediately as detached worker processes with NO queue or concurrency guard (spawnDetachedTaskWorker, codex-companion.mjs:671-710), and the rescue skill defaults to --write (codex-cli-runtime SKILL.md:24,39), so two overlapping writes in one repo is a natural, unguarded pattern. The window is wide (minutes — the whole duration B holds the stream), not a tight race, so it is readily reachable whenever two write runs overlap. This is genuine multi-session mutation of the same tree/index, not serialized away by process boundaries. Corrections to the report: (a) the hazard is specifically write+write — write+read-only-review is safe since a review cannot mutate, so the reviewer's own 'safe for reviews' note narrows the danger to two concurrent writes; (b) directClient is closed in finally (no leak), consistent with the report. Severity is medium rather than high: it silently converts a safe serialization-enforced failure into concurrent mutation that can lose/interleave edits (real data-integrity hazard), but it requires user/agent-initiated concurrent WRITE runs, git's own index.lock partially protects git-level ops (apply_patch/raw edits/shell are unprotected), and there is no crash or security impact. Correct fix: do not fold BROKER_BUSY into shouldRetryDirect the way ENOENT/ECONNREFUSED/connection-closed are — BUSY means another agent is actively holding the app-server, so for workspace-write it should wait/serialize or fail loudly instead of spawning a second direct server.

## [7] MEDIUM · rare · jobs-workers
**Lock-free read-modify-write in updateState + saveState's prune-delete causes lost status transitions and deletion of a concurrently-enqueued job's files (#286)**

- **Location:** `plugins/codex/scripts/lib/state.mjs:124`
- **Interleaving:** updateState does loadState -> mutate -> saveState with no lock; every detached worker and every session calls it (upsertJob on each phase/thread/turn change and on running/completed/failed in tracked-jobs.mjs; enqueue in codex-companion.mjs:698; cancel at :1004). tmp+rename only makes each individual write atomic, not the RMW cycle. Deletion variant: state.json=[A(running)]. (1) Worker A loadState -> [A] (about to emit a progress upsert). (2) Session S1 enqueues job B: writeJobFile(B.json) then upsertJob(B) fully commits -> state.json=[B,A], B.json+B.log created, detached B-worker spawned. (3) Worker A mutates its STALE [A] copy and saveState: previousJobs re-read = [B,A], nextJobs = pruneJobs([A']) = [A'], retainedIds={A}; B is in previousJobs but not retained -> removeJobFile(B.json) + removeFileIfExists(B.log) (state.mjs:106-112), and state.json is rewritten to [A'] with B gone. (4) The B-worker starts handleTaskWorker -> readStoredJob(B) finds no B.json -> throws 'No stored job found for B' and dies.
